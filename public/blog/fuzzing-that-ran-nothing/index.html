Our Go fuzzing ran nothing, and every check was green

3 October 2026 · SilentMesh Systems

On 29 September we added Go fuzz targets for every parser an attacker can reach. CI ran them on every change and every night, and every run was green. For three days, not one of them ran. The step passed in 0.6 seconds. This is how that happened and the rule we added so it cannot happen quietly again.

What the script did

The fuzz step is a short shell script. It lists every Go package, finds each Fuzz function, and runs it for a fixed time:

set -euo pipefail
for pkg in $(go list ./...); do
  ...
  go test -fuzz "^${target}$" -fuzztime "$duration" "$pkg"
done

One of our packages embeds the compiled eBPF object. The fuzz jobs did not build that object first, so go list failed. With set -e and pipefail set, we expected that to stop the script. It does not: a failing command substitution inside a for list is not caught by set -e. The list was empty, the loop ran zero times, and the script exited 0.

How we noticed

Not from a red check. We were reading the nightly runner's logs for an unrelated reason and saw a fuzz step that was meant to run for five minutes per target finish in under a second.

A test that cannot fail tells you nothing. A test that cannot run tells you less, because it looks like a pass.

The fix

  • The fuzz jobs now build the eBPF object before anything else.
  • The script runs go list on its own line and fails if it fails.
  • It counts the targets it ran and fails if the count is zero, then prints the count so a reviewer can see it.
if [ "$ran" -eq 0 ]; then
  echo "fuzz_all: found no Fuzz targets; refusing to pass having fuzzed nothing" >&2
  exit 1
fi
echo "fuzz_all: ran $ran target(s)"

We checked the fix the same way we check our fingerprint probes: delete the eBPF object and confirm the step now goes red. It does.

The rule

Every check that can pass by doing nothing must report how much it did, and must fail when that number is zero. We have since applied the same rule to the decoy fuzz sweep and the kernel test filters. It is the same lesson as our fingerprint tests that could not fail, one layer down: before trusting a green result, prove the check can turn red.
