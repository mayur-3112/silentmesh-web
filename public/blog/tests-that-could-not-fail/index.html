We built decoy fingerprint tests that could not fail

6 September 2026 · SilentMesh Systems

We run eight adversarial probes against our OT decoys. Every one of them was green. Then we built a mode that feeds each probe a decoy broken in exactly the way that probe exists to catch, and required it to fail. Three of the eight results turned out to be facts about the probe rather than facts about the decoy. Here is what was wrong, and what we changed.

What counts as a probe

Decoy work has no natural stopping point. "Make it more realistic" is a slope with no summit, so effort runs until someone gets bored, and gaps get found by accident instead of by test.

Our answer was to define done externally. Each probe in the suite is a real detection technique taken from the published honeypot fingerprinting literature, reduced to a binary PASS or FAIL against our own decoys. The rule the file states about itself:

A decoy is done when every applicable probe passes. If a probe passes, do not gold-plate it. If a probe fails, that is the only work worth doing.

The list being finite and externally derived is what makes it useful. It bounds the work in both directions. We cannot polish forever, and we cannot quietly skip something an attacker actually checks.

There is one more constraint that matters for everything below. A probe has to be something an attacker could run cheaply, without our source code. Every probe states its cost to the attacker in its docstring. A test that requires knowledge only we have is not a probe, it is a unit test.

Green is a claim, not a result

Eight probes, all passing, across four decoys. The reasonable reading is that the decoys survive the published fingerprinting techniques. The other reading is that we wrote eight tests that cannot distinguish anything, and got exactly the same output.

Nothing about a green result tells you which of those you are looking at. You need a second experiment, and the second experiment is the one nobody runs: prove the test can fail.

Self-check: hand each probe the bug it is supposed to catch

So we built --self-check. For each probe, it takes a real decoy, applies a textual mutation to a staged copy that reintroduces exactly the flaw that probe exists to detect, and runs the probe against it. The probe must FAIL. If it passes a decoy we deliberately broke, the probe is reported BROKEN, and its passes everywhere else are discarded. 

Self-check: each probe is run against a decoy deliberately broken
in exactly the way that probe exists to detect. The probe must FAIL.

  [OK]     P1_never_silent          correctly failed the broken decoy
  [OK]     P2_old_protocol_greeting correctly failed the broken decoy
  [OK]     P3_timing_shape          correctly failed the broken decoy
  [OK]     P4_state_vs_time         correctly failed the broken decoy
  ...

The real decoy files are never touched. Mutations apply to a staged copy, following the pattern our decoy decomposition tooling already used.

One detail in the mutation helper is worth pulling out, because it is the same class of bug one level up. A mutation that matched nothing would produce an unmodified decoy. The probe would then correctly pass it, and self-check would report the probe as BROKEN. That is a false accusation caused by the checker, and it is the worst failure mode this file has. So a zero-match substitution is a hard error, with a message telling you the decoy changed shape and the mutation needs fixing rather than the probe.

The rule that came out of this

A test that has never been observed to fail is not evidence. It is a claim that has not yet been tested.

Two probes could not fail

P4, state vs time: both arms were making requests

This probe exists to catch a decoy whose process state advances per request rather than per unit of wall-clock time. A real controller's values move because time passes and the physical process evolves. A lazy decoy increments a counter each time you poll it, and that is fingerprintable: poll it faster, and its world moves faster.

The original design polled a "fast" arm and a "slow" arm and compared two booleans. It was broken twice over.

  • The slow arm's own two reads are themselves two requests. A per-request counter therefore advanced in both arms, so the two booleans could never separate them.
  • The read path carries a 1.0 second drain deadline, which IEC-104 needs for its multi-frame interrogation. That meant the fast arm managed exactly one request inside its two second window.

Staged against the precise per-request counter this probe exists to catch, it passed.

The rebuild dropped the two-arm design entirely. If request-driven state moves by exactly one increment, then a change between back-to-back reads has only one available explanation: the request caused it. That is the whole test. No rate arithmetic, no matched windows, no second arm.

P7, identity uniqueness: it was measuring a clock

This probe exists to catch two deployments that share an identity seed. If every install of a decoy is byte-identical, one fingerprint of one install burns them all.

Self-check staged two instances with the deployment seed pinned to a single constant, making them genuinely the same identity. The probe passed them as distinct. The raw byte comparison was dominated by a counter that ticks once per second, which advances between reads no matter what: 

A  (t=0.00s)  ...0001 0027 0075 41b1 0000
B  (t=1.03s)  ...0001 0027 0076 41b2 0000   <- "different deployment"
A  (t=2.06s)  ...0001 0027 0076 41b3 0000   <- same instance, same delta

B looks different from A. But the second read of A differs from the first read of A by the same amount. The probe was not measuring identity, it was measuring elapsed time.

The fix interleaves reads A, B, A so both gaps are equal and host load hits them equally, then requires the cross-instance difference to exceed the same-instance control. If the test difference is no larger than the control, everything observed is explained by elapsed time and the two deployments are indistinguishable, which is a FAIL.

The obvious alternative, pointing the probe at the handshake instead, is also wrong, and it is worth saying why. Modbus register 0 is a hardcoded constant, so two real PLCs of the same model are identical there too. A probe aimed at the handshake would fail honest decoys for resembling real hardware, which is precisely backwards.

The third one: when the statistic itself is lying

P3 checks the shape of the response time distribution. All four of our decoys sleep on a uniform random delay, so this probe should always have failed them, and it did not. Self-check was built to find out why.

The textbook path is a chi-square test against uniform, ten bins, nine degrees of freedom, and a critical value from the table. The problem is that the samples are quantized. Linux sleep granularity clusters timings onto discrete values, and at roughly 1.9 ms bin width that comb makes bin counts alternate. A genuinely uniform decoy produced: 

bins  [35, 18, 49, 29, 53, 36, 35, 44, 38, 24]

That is a threefold spread from a source that really is uniform. It is a scheduler artefact, not distribution shape, and it inflates chi-square for uniform samples well past where the table says it should sit. Self-check caught the probe waving such a decoy through twice.

We did not fix this by tightening the significance level. Moving from one nominal alpha to a stricter one would have been a number chosen to make the output look right, on a statistic whose assumptions the data violates. Instead the chi-square value is now used as a separator with a measured cut rather than as a significance test, and the constant carries an instruction rather than a citation: 

CRITICAL = 70.0
# Re-derive this number if the delay ranges or the host change;
# do not copy it from a table.

A measured threshold that is honest about being measured is worth more than a textbook threshold that is wrong for your data.

What this changes about our published numbers

We publish a Modbus timing comparison: our decoy answers in about 95.6 ms median against a real OpenPLC controller's 100.9 ms, where the standard open-source honeypot sits at 4.7 ms and a bare software server at 0.8 ms. The argument is that a single timing probe unmasks the fast ones in one pass and does not unmask ours.

That argument depends entirely on our timing tests being able to tell the difference at all. Before self-check, we could not have told you that with a straight face for three of the eight probes. Now we can, for the ones that survived it, and we know exactly which results we had to throw away to get there.

The caveat we attach to those numbers elsewhere still stands unchanged: they come from a single environment across four trials, and they are not a claim about every deployment. Finding this made the numbers more trustworthy. It did not make them universal.

Why there is no public decoy here for you to attack

The natural response to a post like this is: put one on the internet and let us try. We have thought about it, and the honest answer is no, for a reason specific to this product rather than general caution.

Our claim is that a decoy is not distinguishable from real equipment by these techniques. A permanently available public instance is a corpus for learning the answer to exactly that question, ground down at leisure, by anyone. The asymmetry does not favour us: we would be donating the fingerprint surface that the product exists to protect.

What we can do instead is publish the probes' reasoning, the failures we found in our own tests, and the numbers with their caveats attached, which is what this post is. If you think a probe here is weak or a threshold is wrong, that is a conversation we want to have, and the argument can be had on the method without us handing over a grinding target.
