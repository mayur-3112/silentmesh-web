Security

last reviewed 3 October 2026

SilentMesh runs on a network that controls physical equipment, so its first job is to be harmless. This page states what it guarantees, how each guarantee is tested, and what is not done yet.

Report a vulnerability

Email founder@silentmesh.me with "security" in the subject. We reply within two working days, keep you informed until it is fixed, and credit you if you want. Please give us a reasonable time to fix before publishing. Machine-readable contact: /.well-known/security.txt.

How changes ship

  • Nothing reaches the main branch without passing the full gate: build, vet, race detector, decoy tests, the kernel chaos suite on five kernels, fuzzing, a quality ratchet that forbids any metric from getting worse, and a check that published claims match measured numbers.
  • A nightly run repeats the fuzzing for longer, plus soak and longevity tests.
  • An independent penetration test against a live deployment found no remote code execution, no authentication bypass and no unauthorised change to process state. Its two findings were fixed during the engagement.

Not done yet

  • Decoys run as separate supervised processes but do not yet drop root privileges. This is the next hardening step.
  • The console serves plain HTTP unless TLS is configured. Keep it on a management network or enable TLS.
  • Incident records carry a SHA-256 to detect edits after export; the event store itself is not append-only and nothing is signed.
  • IPv4 only. IPv6 passes through untouched and is not intercepted.
  • No third-party security audit or safety certification.
  • No plant runs it yet. Every figure here comes from CI, a lab range and a penetration test; the first pilot turns them into field evidence.
  • Multi-node forwarding is verified across network namespaces on one machine, not yet across separate hosts.
  • Linux 6.6 or newer only, as a Debian package or container image. No RPM yet.
